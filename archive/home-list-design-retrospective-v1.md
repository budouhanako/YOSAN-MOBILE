# Home／一覧画面デザイン振り返り

作成日：2026-08-18  
対象：`internal-budget-home-v1.html`

## 主な問題

1. Axure に存在しない機能や Tab を早い段階で追加し、情報構成より独自判断を優先した。
2. Home と一覧のスタイルを十分に分離せず、一覧の調整が Home に影響する可能性を残した。
3. 初期段階で Axure のボタン名を正確に使用せず、業務名称を独自に変更した。
4. UTF-8 と日本語表示の確認が遅く、途中で文字化けを発生させた。
5. Header、Tab、カード、余白などの共通サイズ規則を先に定義せず、局所的な修正を繰り返した。
6. Unicode 記号をアイコンとして混在させたため、サイズとベースラインが揃わなかった。
7. 小画面への対応を後から追加し、初期版が固定高さ中心の設計になった。
8. 一覧画面のデータ構造、状態、絞り込み、月別集計を先に設計せず、静的 UI から後付けした。
9. CSS、HTML、JavaScript が単一ファイルに集中し、継続開発時の保守性が低い。
10. 各変更後の画面幅、長文、折り畳み、絞り込み、件数更新の組み合わせ確認が不足した。

## 今後の設計方針

- Axure は見た目ではなく、配置、項目、画面遷移、業務構造の基準として扱う。
- ユーザーが指定していない機能、Tab、項目を独自に追加しない。
- 画面に表示する文言は、システムで使用する自然な日本語に統一する。
- 画面ごとの構造とスタイルを分離し、確定済み画面への影響を防ぐ。
- 業務データ、状態、操作、遷移を確認してから視覚設計を行う。
- 共通サイズ規則を先に決める：Header、Tab、ボタン、カード、アイコン、余白、文字サイズ。
- アイコンは同一の線幅、サイズ、デザイン体系で統一する。
- 最初から小画面を基準にし、横スクロールを発生させない。
- 日本語、長い件名、状態ラベル、空データ、絞り込み後の表示を確認する。
- 確定した画面はバージョン付きで保存し、明示的な依頼がない限り変更しない。

## 次画面の確認項目

- 画面の目的と利用者
- Axure 上の必須領域と項目
- 正式な日本語名称
- 入力、参照、編集、承認などの操作区分
- 状態と状態遷移
- 必須項目と入力形式
- 前画面、次画面、戻る動作
- 小画面での表示優先順位
- Home／一覧との共通部分
- 確定済み画面へ影響しない実装範囲

# 執行伺作成画面デザイン振り返り

対象：`internal-budget-execution-create.html`

## 確定した設計

### 画面遷移

- Home の `執行伺入力` から作成画面へ遷移する。
- 最初に `様式を選択` Dialog を表示する。
- 様式を選択してから多段階入力を開始する。
- `戻る` と `キャンセル` では、確認後に Home へ戻る。
- Home／一覧 V1 は作成画面の変更対象に含めない。

### 入力ステップ

1. `基本情報`
2. `執行内容`
3. `執行明細`
4. `予算確認`

上部には軽量なステップ進捗のみを表示し、業務状態は表示しない。

### 基本情報画面

画面を次の三つの折り畳み領域に分ける。

- `基本情報`
- `備考`
- `添付ファイル`

各領域のタイトルは黒色太字、背景は薄紫色、右側に折り畳み矢印を表示する。

### 基本情報の項目

- `申請様式`：変更不可
- `申請番号`：編集可能、最大8桁
- `申請年度`
- `申請日`
- `入力者`：Disabled、変更不可
- `部門` と `部門配分パターン`：同一行
- `部所` と `目的`：次の行
- `申請者`
- `執行理由`
- `内容`

### 必須項目

- 必須項目は赤色の星形 Icon で示す。
- Icon は Label 名称の右側に表示する。
- Label は黒色太字とする。
- Label の高さと入力欄までの余白は小さく保つ。

### 備考領域

Web 画面の業務項目を省略せず、次の三グループを表示する。

- `状態1～状態5`：日付入力
- `項目1～項目6`：テキスト入力
- `備考`：複数行入力

スマートフォンでは状態と項目を二列で表示する。各サブタイトルと入力欄の間には薄紫色の点線を表示する。

### スマートフォン向け変換

- Web の横長 Grid はそのまま使用しない。
- `執行内容` と `執行明細` は追加・削除可能な Panel 形式にする。
- 単価、数量、金額、摘要などを Panel 内に配置する。
- 金額と予算残高は自動計算する。
- 業務項目を維持した上で、折り畳み、二列配置、固定操作欄で高さを抑える。

## 設計中に発生した問題

1. Web の Tab とスマートフォンのステップの対応を先に整理しなかった。
2. 状態表示を進捗領域とタイトル領域に追加したが、情報階層と画面高さに合わず、最終的に削除した。
3. 初期案では備考を単一テキスト欄として扱い、`状態1～5` と `項目1～6` を見落とした。
4. `申請番号` を誤って読み取り専用にし、`入力者` を編集可能にした。項目属性の確認が不足していた。
5. 部門関連項目の並びを Web の業務内容と照合せず、後から修正した。
6. 項目数が多い画面に対し、初期段階で高さとスクロールを十分に設計しなかった。

## 今後の作成画面設計ルール

- デザイン前に Web 項目との対応表を作成する。
- 各項目について、必須、編集可否、型、初期値、候補値、連動先を確認する。
- Web の Tab、Grid、Panel をスマートフォンでどう再構成するか先に決める。
- 指定されていない状態や補助情報を独自に追加しない。
- Label、必須 Icon、Section Title、折り畳み、底部操作欄のスタイルを共通化する。
- 小画面で長い日本語、入力エラー、Disabled、空データ、明細追加時の表示を確認する。
## 2026-08-19 追加复盘

- 当前文件是 Base64 封装的多页面原型，不能按普通 HTML 直接替换。
- 每次修改前应先保存快照，修改后解码检查，并打开对应的 `#create` 页面确认实际效果。
- 一次只修改一个明确目标，避免连续追加脚本影响既有布局和交互。
- AI、附件、进度条、基本情報的层级必须先确认，再进行 DOM 调整。
- 附件 panel 的折叠应复用基本情報 panel 的统一 `.section` / `.section-title` 机制。
- 不能把“文件已写入”当作“画面已完成”，必须以浏览器实际显示为准。
- 返回按钮应先确认宿主页面通信方式，再决定使用 `postMessage` 或 URL 跳转。
- 报告完成前需要验证元素、按钮、折叠高度和不同 step 的显示状态。
